Step 1

What this is, and the four ideas

The product in one paragraph, then the four concepts that every table, policy and function in the system follows from.

The product

Mars Pharmacy ERP — a multi-entity pharmacy ERP. Next.js 16 (App Router) on the front, Supabase / PostgreSQL 15 behind it.

“Multi-entity” is the core business framing: one entity = one independently operated pharmacy. Ten pharmacies share one installation and one database, but no pharmacy can see another's stock, sales, costs, or staff.

The one naming inconsistency

The database column is branch_id everywhere; the UI labels it Entity. Remember that mapping — you will have to explain it if anyone reads the SQL alongside the screens.

Scale of what is built: 36 tables, 2 views, 97 RLS policies, 9 transactional RPCs, 17 migrations.

The four load-bearing ideas

If the audience remembers only four things, these are the four. Everything else in the schema is a consequence of them.

1Entity is the isolation boundary

Every entity-owned table carries branch_id NOT NULL. Isolation is not enforced by careful queries in application code — it is enforced by row-level security in the database. Even if the app had a bug and asked for another pharmacy's rows, Postgres returns zero rows.

2Stock lives on batches, never on products

products is a catalogue — name, pack size, price. It has no quantity column. Physical stock lives in product_batches, where each row is one real lot with its own cost, its own expiry date and its own quantity.

This is non-negotiable for pharmacy: two boxes of the same medicine bought at different prices and expiring in different months are genuinely different things. Each batch also records which document created it (source_type / source_id), so any unit of stock traces back to its origin.

3The ledger is the truth

Every single stock change appends a row to stock_movements, recording the balance_after. Nothing is ever updated or deleted there.

The invariant: summing the ledger for a batch equals that batch's quantity_available — always. That is asserted in the test suite, so it is a checked claim, not an aspiration. When someone asks “how do you know your stock numbers are right?”, this is the answer.

4Documents go draft → confirmed

A stock document (opening stock, inward, sale, return) is freely editable while status = 'draft'. Nothing moves stock while it is a draft.

Confirming it calls a database function that, in one transaction, creates the batches, writes the ledger rows, and locks the document. After that it is immutable. So stock only ever moves through one narrow, audited, all-or-nothing door.

How they fit together

Read it top-down: the entity owns everything. Products and suppliers are reference data. Batches are the real stock. Documents are the events that create or consume batches. The ledger records every one of those events.

Step 2

The file map and the request flow

Three route entry points, four layers, and one function that answers “who is this and what may they see” for every screen in the application.

The shape of the app

Only three route entry points exist. That surprises people, so lead with it.

RouteFileWhat it serves
/loginsrc/app/login/page.tsxSign-in
/dashboard/*src/app/dashboard/[[...section]]/page.tsxAll 24 screens
/api/*src/app/api/3 routes: AI chat, import template download, report export

That [[...section]] is an optional catch-all route. /dashboard/sales, /dashboard/inventory, /dashboard/reports — all one file. It reads the section name from the URL and dispatches.

So there is one place where auth, permissions and entity context get resolved, instead of 24 places that each might forget.

The four layers

  src/app/dashboard/views/          29 files   ← what it looks like (client)
  src/app/dashboard/actions/        19 files   ← writes  (server actions)
  src/lib/data/                     25 files   ← reads   (loaders)
  src/lib/  +  supabase/migrations/            ← rules   (shared logic + DB)
The discipline

Views never touch the database. Reads go through lib/data/, writes go through actions/. A view receives data as props and calls an action on submit. That is the whole rule.

The flow — reading a screen

Someone opens /dashboard/sales-history:

1. proxy.ts                        refresh the session cookie
2. page.tsx   requireUser()        who is this? → redirect to /login if nobody
3. page.tsx   permittedSections()  may they see this section? → redirect if not
4. lib/data/sales.ts  getScope()   which entity? what may they see?
5. supabase.from("sales")…         Postgres applies RLS
6. AppShell → sales-history-view.tsx   render

Step 4 is the one worth dwelling on. getScope() in src/lib/data/scope.ts is called by every single loader and returns one bundle:

{ supabase, employee, entityId, entityName, currency,
  canViewCost, canViewProfit, canViewReports, canExport }

So “which pharmacy am I looking at” and “am I allowed to see cost and profit” are answered once, in one function, for all 25 loaders. No loader improvises.

The flow — writing (completing a sale)

1. sales-view.tsx      calls completeSale(…)
2. actions/sales.ts    requireUser()
3.                     permissionError(employee, "create_sales")   ← gate
4.                     supabase.rpc("erp_complete_sale", {…})      ← one DB call
5.                     revalidatePath(…) × 5                       ← refresh screens

Every write action is that same five-line skeleton. And note step 4: the action does not insert a sale row, then decrement batches, then write ledger rows. It makes one call to a database function that does all of it in one transaction.

That is the draft→confirmed idea from Step 1 showing up in the code — the app cannot half-complete a sale, because it does not have the ability to do the pieces separately.

Step 3 · Schema A

Entities, employees, roles, permissions

Five tables. That is the whole access-control model — understand these and you can answer any “who can do what” question.

  branches  ─────────┐
   (entity)          │ branch_id = home entity
                     │
  employees ─────────┤
       │             └─── employee_entities   (extra entities, many-to-many)
       │ role
       ▼
  role_permissions        (role → permissions, the template)
       +
  employees.permission_overrides   (per-person tweaks)
       ↓  filtered by
  permission_catalog      (which permissions may be tweaked at all)

1. branches — the entity

One row = one pharmacy.

Per-entity currency and timezone matter — the same installation can run pharmacies in different countries, and each one's reports come out in its own currency.

2. employees — the person

Two things to point out:

  • Login and employee are separate. Supabase Auth holds the password; employees holds the business identity. auth_user_id joins them. A disabled employee can still authenticate but gets nothing — the DAL rejects any status other than active.
  • max_discount_percent is per-person, not per-role. So a senior cashier can be trusted with 15% while a new one gets 5%, without inventing new roles.

3. The four roles

RoleIn one line
master_adminOwns the whole installation. Sees all entities. The only role that can create entities.
entity_adminOwns one pharmacy completely. Cannot create entities or reach other ones.
inventory_userBuys and stocks. Products, suppliers, inward, stock-out. Cannot sell.
sales_userDispenses at the counter. Cannot see purchase cost or profit.
The two commercially important separations

The person at the counter cannot see what you paid for the medicine or what you make on it.

The person who buys stock cannot ring up sales, so nobody controls both sides of a transaction.

4. Where permissions live

Three pieces, and the layering is the point.

role_permissions — the template

(role, permission) composite PK, 53 rows = 4 roles × their permissions. Seeded in migration 0006, and it is the runtime source of truth — not a constant in the code.

employees.permission_overrides — the exceptions

Per-person adjustments on top. {"apply_discount": true} grants it; {"view_profit": false} revokes it. So you rarely need to invent a new role: you take the nearest one and adjust.

permission_catalog — what may be adjusted at all

permission PK, overridable bool, all 21 permissions. Three are overridable = false:

manage_users  ·  manage_entities  ·  access_multiple_entities
Why this table exists

These three are role-only, never grantable by override. Without this, anyone holding manage_users could hand themselves — or a colleague — master-level reach by writing one JSON key. That is the classic privilege-escalation hole, closed by data rather than by code review.

employee_entities — extra access

(employee_id, branch_id) composite PK. Grants a person access beyond their home entity. Master admins need no rows here; they see everything by role.

7. How a permission check resolves

The rule: role template first, then overrides on top — but overrides are ignored for the three non-overridable permissions.

That rule is implemented twice, deliberately:

  • In TypeScript — resolvePermissions() in src/lib/permissions.ts, which decides what the UI renders and what actions accept.
  • In SQL — has_perm(text), which every one of the 97 RLS policies calls.

They are not duplicated by accident. The TypeScript copy gives a clean UI and a friendly error message; the SQL copy is the one that actually protects the data. If someone bypassed the app entirely and hit the API directly, has_perm still runs.

And there is a third guard: the employees_guard trigger rejects a non-overridable override at write time, on every path — including the service-role key that bypasses RLS. So a bad override cannot be stored, cannot be read, and would not work if it somehow existed.

One-sentence version

Four roles give you the defaults, per-person overrides handle the exceptions, three master-tier permissions are locked out of the override mechanism entirely, and the same resolution rule is enforced independently in the app and in the database.

Step 4 · Schema B

Products, batches, documents, the ledger

The operational heart of the system. Everything here exists to make one claim true — and the claim is at the end of this step.

   products          catalogue — no quantity, ever
      │
      ▼
   product_batches   the real stock: one lot, one cost, one expiry
      ▲     ▲
      │     └──────────── documents CONSUME batches (sales, returns)
      │
   documents CREATE batches (opening stock, inward, GRN)
      │
      ▼
   stock_movements   append-only ledger — every change, with balance_after

1. products — the catalogue

ColumnNotes
skuUNIQUE (branch_id, sku) — per entity, not global
name, generic_name, strength, form, unit, barcode, manufacturertext
category_id, supplier_iduuid FK
buy_priceLOCKED SELECT revoked from authenticated
sell_pricenumeric
pricing_methodfixed | cost_plus_margin
margin_percentused when cost_plus_margin
max_discount_percentper-product ceiling
reorder_level / restock_targetwhen to reorder / reorder up to
statusactive | discontinued | quarantined

Three things to flag:

  • No quantity column. Deliberate. Stock is never on the product.
  • SKUs are unique per entity. Two pharmacies can both use PARA-500 for their own products without collision.
  • buy_price has SELECT revoked at the database level. Not hidden by a query — revoked. A sales user's connection cannot read that column at all.
Two discount ceilings

products.max_discount_percent (this medicine) and employees.max_discount_percent (this cashier). A sale must satisfy both — checked inside erp_complete_sale, not in the browser.

product_price_history logs every change to buy_price, sell_price, margin_percent, pricing_method and max_discount_percent — with old value, new value, who, and why. Rows where field = 'buy_price' require view_purchase_cost to read.

2. product_batches — the real stock

ColumnNotes
product_id, branch_iduuid NOT NULL
batch_numbertext NOT NULL
supplier_iduuid FK
quantity_receivedas delivered
quantity_availableLOCKED UPDATE revoked — ledger-derived
unit_costLOCKED SELECT revoked from authenticated
expiry_date, storage_locationdate, text
statusactive | quarantined | damaged | expired | negative
source_type / source_idthe document that created this batch
The most important revocation in the schema

quantity_available has UPDATE revoked. Nobody — no user, no app code, no admin screen — can write a number into that column. It only moves when a ledger row is posted. That single revocation is what makes “the ledger is the truth” a structural fact rather than a convention.

source_type / source_id give full traceability: any batch on the shelf points back to the document that brought it in. Pharmacy regulators ask for exactly this.

3. Stock IN — three doors, all draft → confirm

A. opening_stock_entries → opening_stock_items

Day-one stock when a pharmacy joins the system. Line carries product_id, batch_number, expiry_date, quantity (CHECK > 0), unit_cost, optional sell_price.

Confirm: erp_confirm_opening_stock(id) → one batch per line, posts opening_stock movements, locks the entry.

B. stock_inwards → stock_inward_items

Routine goods receipt. Four inward_type values:

purchase_from_parent · purchase_from_external · foc_or_sample · replacement_in

Each line has both quantity and free_quantity — paid units and free units on the same line, with CHECK (quantity + free_quantity > 0).

Confirm: erp_confirm_stock_inward(id). Paid units post as purchase; free units post as a separate foc movement.

A differentiator worth naming

Free goods stay identifiable in the ledger forever — so you can answer “how much of our margin came from free stock?” That is a real pharmacy-distribution question and most systems cannot answer it.

Also: UNIQUE (branch, supplier, invoice_number) while not cancelled — the same supplier invoice cannot be received twice.

C. purchase_orders → received_orders

The formal PO path.

PO status:  draft → pending_approval → approved → partially_received
            → received | cancelled

The GRN (received_orders) carries quantity_ordered, quantity_received and damaged_qty per line, with status partial | complete | variance.

Receive: erp_receive_purchase_order(po_id, supplier_invoice, lines).

4. Stock OUT

sales → sale_items

ColumnNotes
invoice_numberUNIQUE
customer_id, cashier_iduuid FK
payment_methodCash | Bank | M-Pesa | Selcom | Credit
subtotal, discount, tax, totalalways derived server-side
statuscompleted | returned | reversed
request_keyUNIQUE (branch_id, request_key) — idempotency
  • Money is never trusted from the browser. The client sends product ids and quantities; erp_complete_sale computes every figure from the database. A tampered request cannot change a price.
  • request_key is a double-click guard. Same key twice = the original sale returned, not a second one. Enforced by a unique index, so it holds even under a race.
  • sale_items is immutable — no UPDATE or DELETE policy exists.

Cancelling a sale calls erp_reverse_sale(sale_id, reason), which never deletes. It posts sale_reversal movements and stamps reversed_by / reversed_at / reversal_reason. Nothing disappears from the record.

returns — one table for every stock-out document

typeReal-world eventStock effect

Status: pending → approved | review | rejected | completed. Approve with erp_approve_stock_out(return_id) — which needs approve_stock_outward, a permission inventory users do not have.

Why one table: all five are “stock leaves or returns with a documented reason and a named approver.” So they share one approval flow, one audit trail, one screen — and the type column keeps them distinct in the ledger.

stock_transfers

Move a batch between entities. erp_transfer_stock(batch_id, to_branch, quantity) posts both transfer_out and transfer_in legs atomically. Never one without the other.

5. stock_movements — the ledger

Locked down

SELECT only. No INSERT / UPDATE / DELETE policy and the privileges are revoked from authenticated. There is exactly one writer: fn_post_movement, which is revoked from every client role and callable only from inside an erp_* RPC.

So the ledger cannot be written by the app, by a user, or by an admin screen. Only by a database function reached through one of the nine transactional RPCs.

The stock equation

closing stock = opening_stock
              + purchase + foc + replacement_in + transfer_in
              − sale − employee_consumption − expiry − damage
              − supplier_return − transfer_out
              + sale_reversal
              ± stock_correction

And it is tested. The suite asserts the ledger sums exactly to product_batches.quantity_available, and that balance_after forms an unbroken chain. If anything ever broke the invariant, the tests fail.

Imports never create sellable products directly

Rows land in draft_products as pending and become real products only when a user with create_products confirms them. product_imports carries UNIQUE (branch_id, kind, file_hash) — the same file cannot be imported twice into one entity, whatever it is renamed to.

Limits: 5 MB, 5 000 rows, .xlsx / .csv only. Rows are re-validated and sell price recomputed at commit, because the payload round-trips through the browser.

Document numbering

Six sequences — doc_seq_sale, doc_seq_inward, doc_seq_opening, doc_seq_return, doc_seq_correction, doc_seq_import — issued by next_doc_number(prefix, seq) → INV-2026-000123. Collision-proof under concurrency.

The claim this all buys you

For any unit of stock, you can answer: where did it come from, what did it cost, when does it expire, who touched it, and where did it go — and the numbers are arithmetically guaranteed to reconcile.

That is the sentence to say out loud. Everything in this step exists to make it true.

Step 5

The security model

Five enforcement layers, every one of them inside PostgreSQL. The application layer is for user experience, not for defence.

Start with the threat model

Say this first

The browser holds the anon key and the user's JWT. So nothing in the client is a security control.

It is the sentence that makes the rest make sense. Anyone with devtools can read the anon key out of the page and hit the Supabase REST API directly — skipping the login page, the React code, the server actions, all of it.

So the question is never “does the UI hide it?” It is: what happens when someone talks straight to the database?

Browser (hostile)  ──▶  Server Actions        ──┐
                   ──▶  Direct PostgREST      ──┤  ← the real threat model
                                                ▼
   LAYER 1  Column privileges    buy_price / unit_cost not selectable
   LAYER 2  RLS · 97 policies    has_entity_access() AND has_perm()
   LAYER 3  Permission resolution   role + overrides + catalogue
   LAYER 4  Transactional RPCs   permission → entity → consistency → lock
   TRIGGERS  fire on every path, service role included

Layer 1 — Column privileges

The strongest thing available, and used in exactly three places.

TargetRevoked
products.buy_priceSELECT from authenticated
product_batches.unit_costSELECT from authenticated
product_batches.quantity_availableUPDATE from authenticated

This is stronger than a policy. A policy filters rows; this removes the column from the role's reach. A sales user asking for buy_price does not get null — they get an error, because that column is not theirs to name.

Cost is reachable only through two views:

create view product_costs with (security_invoker = false) as
select p.id as product_id, p.branch_id, p.buy_price
from products p
where has_entity_access(p.branch_id)
  and has_perm('view_purchase_cost');

batch_costs is the same shape for unit_cost. Without the permission you get zero rows — not a nulled column, not a masked value. The data does not exist for you.

Maintenance note

Column privileges are role-wide, so the pattern is revoke table SELECT, then grant back the permitted columns. fn_grant_readable_columns(table, exclude[]) does that, and must be re-run whenever a column is added to either table.

Layer 2 — Row-level security

Enabled on 36 / 36 tables. 97 policies. No exceptions.

Every policy composes the same two functions:

has_entity_access(branch_id)   AND   has_perm('view_inventory')
       ↑                                    ↑
   which pharmacy?                    which capability?

Two tables are SELECT-only by design: stock_movements (the ledger) and document_embeddings.

has_entity_access(uuid) is true for a master admin, or when the branch is the employee's own, or when it is granted via employee_entities. And one detail worth stating: has_entity_access(NULL) returns false. Null is not a wildcard. A row with no entity is invisible to everyone rather than visible to everyone — that was a real finding, fixed in migration 0017.

Layer 3 — Permission resolution

has_perm(text) is the SQL half of what Step 3 described:

select case
  when e.permission_overrides ? p
   and coalesce((select pc.overridable from permission_catalog pc
                 where pc.permission = p), false)
  then (e.permission_overrides ->> p)::boolean
  else exists (select 1 from role_permissions rp
               where rp.role = e.role and rp.permission = p)
end
from employees e
where e.auth_user_id = auth.uid() and e.status = 'active'

Read it out loud: use the override only if the catalogue says this permission is overridable; otherwise fall back to the role template. A planted {"manage_entities": true} is ignored at read time, not just rejected at write time.

Note e.status = 'active' — a disabled employee resolves to no permissions at all, at the database level.

Every one validates in the same order

permission → entity access → document status → branch consistency
→ business rules → row locks → ledger → commit

Branch consistency (migration 0013) is the subtle one: it checks that the batch, product and supplier all belong to the document's entity. Without it you could reference your own entity's document while pointing at another entity's batch — passing every individual check while still crossing the boundary.

Row locks — SELECT … FOR UPDATE — mean two cashiers selling the last box at the same instant cannot both succeed. And fn_post_movement refuses to take stock negative, under that lock.

The triggers — the layer that ignores the service-role key

employees_guard (BEFORE INSERT OR UPDATE)

  1. Rejects non-overridable keys, unknown keys and non-boolean values in permission_overrides — on every path, including the service role
  2. Nobody may change privilege columns on their own row, whatever permissions they hold (role, permission_overrides, max_discount_percent, branch_id, approval_limit, status)
  3. Non-master privilege writes must satisfy has_entity_access on both the old and the new branch — so you cannot move someone into your entity to gain control of them, or out of it
  4. Only a master admin may grant master_admin or change auth_user_id

employees_protect_last_master (BEFORE UPDATE)

The last active master admin cannot be disabled or demoted. No locking yourself out of your own installation.

Why “service role included” matters

RLS is bypassed by the service-role key. Triggers are not. So these rules hold even for code paths that hold the god key.

Storage

Buckets product-images and stock-documents: private, 10 MB cap, MIME allowlist (PNG / JPEG / WebP / GIF / PDF). Read, write and delete are confined to a <branch_id>/… path prefix the caller can actually access — entity isolation extends to files.

Questions you should expect, and the answers

What stops a developer, or someone with devtools, bypassing the app?

Nothing needs to stop them — the app is not the control. The browser already holds the anon key. Every rule lives in Postgres: 97 RLS policies, revoked column privileges, and nine transactional functions. And 74 of our tests are written from exactly that attacker's position, signing in with the anon key and hitting the REST API directly.

Could an entity admin promote themselves to master admin?

No, in three independent ways. Master-tier permissions are marked non-overridable in permission_catalog. A trigger rejects the write. And has_perm ignores such an override even if it somehow existed. On top of that, nobody can edit privilege columns on their own row, whatever their permissions.

What if two cashiers sell the last box at the same time?

One succeeds, one gets an error. The sale function takes a row lock on the batch, and the ledger writer refuses to go negative under that lock.

What if a cashier double-clicks Complete Sale?

One sale. Each submission carries a request key with a unique constraint on (branch_id, request_key) — the second attempt returns the original sale rather than creating a new one. Enforced by a unique index, so it holds under a race, not just under a check.

Can someone delete a sale to hide it?

No. sale_items has no UPDATE or DELETE policy at all. Cancelling posts reversal movements and stamps who reversed it, when, and why. Nothing is ever removed from the record.

Why one returns table for five different things?

Because customer returns, supplier returns, damage, expiry and staff consumption are all the same shape: stock moves with a documented reason and a named approver. One table means one approval flow, one audit trail, one screen — and the type column keeps them distinct in the ledger.

Is it production-ready?

The enforcement model is sound and tested. Four things are outstanding: credentials exposed during development need rotating — that is the highest risk and it is a decision I need from you; a dedicated test project needs creating; browser-level QA has not been done; and there are 3 high-severity dependency advisories, no critical.

If you remember only one paragraph

Each pharmacy is an isolated entity. Stock lives on batches with their own cost and expiry, never on products. Every stock change appends to a ledger that the application itself cannot write to, and the ledger provably reconciles to on-hand quantity. Documents do not move stock until they are confirmed, and confirming is one all-or-nothing database transaction. Purchase cost is revoked at the column level for counter staff, and no user can raise their own privileges. All of it is enforced in PostgreSQL, and 74 tests attack it the way an attacker actually would.
